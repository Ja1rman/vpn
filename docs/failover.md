# Основной и резервные VPN-выходы

`inventory/hosts.json`: `balancer.strategy = "priority"`. Весь новый пользовательский трафик использует первый доступный выход. Ротации по соединениям между исправными выходами нет.

Порядок приоритетов:

1. Порядок хостов в `nodes`.
2. Порядок транспортов в `outbounds` каждого хоста.

Текущий основной — `breeze-reef` VLESS/REALITY/XHTTP443 (`pool-breeze-reef-0`). Резерв — Hysteria UDP55625 (`pool-breeze-reef-hysteria-v2`) **того же VPS**. Оба используют физический NL-хост `144.31.34.165`. Для продолжения работы при полном отказе VPS требуется добавить независимый хост; команда `add_host.py` добавляет его в конец списка резервов.

Private Hysteria outbound содержит тот же Salamander mask, что и сервер. Его пароль хранится только в `.local/outbounds/` и GitHub Secret `VPN_OUTBOUNDS_JSON`. В текущей паре версий Xray нативные Hysteria UDP DATAGRAM показали нестабильную доставку. Поэтому только для этого резерва UDP передаётся через XUDP в Hysteria streams: `mux.enabled=true`, `concurrency=-1`, `xudpConcurrency=16`, `xudpProxyUDP443=allow`. Обычный TCP не мультиплексируется. Настройки NL-сервера и клиентских VPN-профилей для этого не меняются. Потоки надёжного транспорта могут увеличивать задержку UDP при потерях; основной VLESS этим изменением не затронут.

## Переключение и восстановление

Observatory проверяет HTTP через каждый настоящий outbound каждые 10 секунд. При недоступности основного новые соединения идут через следующий доступный. При восстановлении более приоритетного выхода новые соединения снова выбирают его. Старые живые сессии не разрываются принудительно и могут некоторое время оставаться на резерве. При отказе самого сервера существующие TCP-сессии обрываются, приложение устанавливает их заново; новая сессия может иметь другой внешний IP.

Таким образом, IP не меняется на каждом запросе при исправном основном выходе. Смена при реальном отказе или восстановлении и временное сосуществование ещё открытых сессий возможны. Проверки доступности продолжаются на резервных хостах и не используют cookies/учётные записи пользовательских приложений.

## Как устроена цепочка

У каждого balancer один selector и один подходящий tag. Основной `vpn-pool` выбирает только `pool-breeze-reef-0`. Если он недоступен, `fallbackTag=failover-hop-1` возвращает поток в маршрутизацию через native outbound `loopback`, с новым inbound tag `pool-fallback-1`. Это правило выбирает следующую ступень с одним резервом. Конец цепочки — `blocked`.

Внутренний Xray strategy type называется `roundRobin`, но один кандидат на ступени исключает чередование. На старте tag без первого результата проверки считается доступным самим Xray, поэтому до первого probe возможна попытка соединиться с ещё не проверенным основным. После наблюдения применяется обычный приоритетный failover. Нет дополнительного внешнего контроллера и зависимости от Python-процесса для постоянной работы.

Selectors Xray сопоставляют префиксы. Генератор отклоняет неоднозначные имена, например tags, где `pool-x-1` совпадает также с `pool-x-10`, чтобы случайно не включить распределение. После hot reload updater дополнительно проверяет фактических кандидатов API, включая сохранённые старые handlers. Для явного постоянного tag используйте `node.outbound_tags`: словарь путь outbound → tag с префиксом `pool-`. Это также позволяет исправить/обновить транспорт под новым tag, сохранив старый обработчик для завершения его сессий.

## Изменить основной хост или порядок резервов

Для смены основного хоста переставьте **хосты** в `nodes`. Массив файлов `outbounds` существующего узла не переставляйте: его индексы определяют постоянные tags. Для другого приоритета транспорта задайте, например, `balancer.priority_order: ["pool-breeze-reef-hysteria-v2"]`: этот tag станет первым, остальные сохранят обычный порядок. Поле принимает уникальные существующие tags; новые хосты всё равно добавляются в конец. Затем:

```bash
python3 scripts/render.py
python3 scripts/vpnctl.py update-pool
```

Основной x-ui и клиентские входы не изменяются. Loopback bridges добавляются API без перезапуска; устаревшие обработчики сохраняются для завершения живых сессий. Закреплённые API и SOCKS listen-порты не меняются. Если меняете сами реквизиты выхода, используйте новое имя узла.

При добавлении VPS через `add_host.py` он становится резервным по порядку inventory. Для будущего CI обновите GitHub Secrets через `sync_github_secrets.py`; deploy по-прежнему ручной и выключен до разрешения владельца.

## Проверки

`scripts/test_priority_failover.py` создаёт изолированные три VLESS-выхода и HTTP/UDP echo-сервисы только на loopback. Все здоровы → только A; отказ A → только B; отказ A+B → только C; восстановление A → только A; отказ всех → блокировка. Проверяются повторные TCP-запросы и UDP на каждой ступени. Рабочие сервисы не останавливаются.

`scripts/verify_priority_backup.py --expected-ip 144.31.34.165` запускает отдельный клон реального пула на временных loopback-портах. Только в этом клоне основной адрес заменяется на неслушающий порт; проверяются четыре HTTPS-запроса через реальный резервный транспорт и четыре отдельных UDP DNS-ассоциации. Рабочая конфигурация не меняется.

## Снимки и откат

Снимок до перехода: `/var/backups/vpn-infra/pool-20261016T134014981335Z/before.json`. Снимок после — `after.json`; отметка `committed` подтверждает проверки. Для ручного возврата на прежнюю схему через SSH входного сервера:

```bash
sudo python3 /opt/vpn-infra/staging/entry/balancer/update_pool.py \
  /var/backups/vpn-infra/pool-20261016T134014981335Z/before.json
```

Команда также использует watchdog и проверку TCP/UDP. Не возвращайте устаревший снимок после добавления/изменения узлов без просмотра различий. После ручного отката приведите inventory в соответствие с выбранной схемой, иначе следующий render/deploy восстановит priority.
