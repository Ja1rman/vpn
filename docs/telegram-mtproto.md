# Telegram MTProto с резервными выходами

Есть дополнительный **MTProto DD** на `${VPN_ENTRY_ADDRESS}:${VPN_MTPROTO_DD_PORT}`. Ссылка находится в `.local/mtproto-dd/access.md`. DD использует тот же приоритетный VPN Auto пул и отдельную службу `vpn-mtproto-dd.service`; исходный FakeTLS-вход сохранён. Режим проверен настоящим клиентским стеком Telegram, включая полный обмен ключами и служебный RPC, без входа в аккаунт. Работа без VPN именно в проблемной Wi-Fi-сети пользователя пока не подтверждена: на тестовом Mac действует прозрачный Network Extension, который может перехватывать сокеты с выбранным физическим интерфейсом.

Telegram подключается к одному адресу `${VPN_ENTRY_ADDRESS}:${VPN_MTPROTO_PUBLIC_PORT}`. Новый TCP-вход передаёт MTProto на существующий локальный backend `${VPN_LOOPBACK_IP}:${VPN_MTPROTO_PORT}`. Служба `vpn-mtproto.service` отправляет соединения через SOCKS `${VPN_LOOPBACK_IP}:${VPN_FAILOVER_SOCKS_PORT}` существующего **VPN Auto**. Исходящий порядок берётся из `inventory/hosts.json → failover.egresses`: **ihor → breeze-reef → srv-41969**. Пока основной выход исправен, новые соединения используют его; распределения между исправными хостами нет.

Прокси действует внутри Telegram. При отказе выхода Telegram восстанавливает оборванное соединение, и новая попытка идёт через доступный резерв после обновления проверок пула. У всех выходов общий входной сервер `${VPN_ENTRY_ADDRESS}`; для резервирования его полного отказа потребуется второй вход. При недоступности всего пула соединение отклоняется.

## Установка с ноутбука

Из папки проекта с настроенным SSH-доступом к входному серверу:

```bash
python3 scripts/vpnctl.py deploy-mtproto
```

Команда создаёт секрет при первом запуске и сохраняет его для следующих развёртываний. Используются закреплённый бинарник **mtg 2.3.0** и отдельная systemd-служба. Она также устанавливает `vpn-telegram-socks.service`: публичный MTProto TCP-вход и отдельный SOCKS5 с логином и паролем. Переменная `VPN_MTPROTO_SECRET` позволяет передать существующий секрет из защищённого окружения. Для SOCKS5 используются `VPN_TELEGRAM_SOCKS_USERNAME` и `VPN_TELEGRAM_SOCKS_PASSWORD`. В GitHub Actions подготовлен отдельный ручной компонент `mtproto`, получающий эти значения из Secrets окружения `production`.

Если в закрытом окружении задан `VPN_MTPROTO_DD_PORT`, команда также устанавливает DD. Отдельно этот компонент разворачивается так:

```bash
python3 scripts/vpnctl.py deploy-mtproto-dd
```

Используются закреплённые commit/SHA256 проекта [alexbers/mtprotoproxy](https://github.com/alexbers/mtprotoproxy) и wheel PySocks. Архивы проверяются до установки и сохраняются в `.local/mtproto-dd/assets/`; зависимости не устанавливаются в системный Python. На сервере должен быть доступен `python3-cryptography`. Служба работает отдельным непривилегированным пользователем, поддерживает только secure DD и использует Auto SOCKS как единственный выход. Ключ выводится из действующего MTProto-секрета, адреса и секреты исходных подключений сохраняются. Повторный запуск проверяет точное совпадение файлов и службы без рестарта.

Закрытые файлы на ноутбуке:

| Файл | Содержимое |
| --- | --- |
| `.local/mtproto/access.md` | Готовая инструкция и ссылки для подключения |
| `.local/mtproto/access.json` | Адрес, порт, домен маскировки, секрет и ссылки |
| `.local/mtproto/config.toml` | Копия конфигурации установленного прокси |
| `.local/mtproto-dd/access.md` | Готовая ссылка MTProto DD |
| `.local/mtproto-dd/access.json` | Адрес, порт и DD-секрет |
| `.local/mtproto-dd/config.py` | Закрытая конфигурация отдельной DD-службы |
| `.local/telegram-socks/access.md` | Ссылка для добавления SOCKS5 в Telegram |
| `.local/telegram-socks/access.json` | Адрес, порт, логин, пароль и ссылки SOCKS5 |

Секрет имеет формат Fake TLS: `ee` + 16 случайных байт в hex + домен `yandex.ru` в hex. Это секрет доступа, а не пароль учётной записи Telegram. Не публикуйте ссылки и содержимое этих файлов: они дают доступ к прокси. Каталог `.local/` исключён из Git, закрытые файлы должны иметь права `600`. Не удаляйте `access.json` ради повторной установки: смена секрета потребует обновить настройки всех клиентов. В репозиторий добавляются только код и документация; секрет для автоматизации передаётся через защищённые переменные окружения/Secrets.

## Подключение Telegram

Откройте ссылку из `.local/mtproto/access.md` на устройстве с Telegram и включите прокси. Либо в настройках Telegram выберите **Данные и память → Прокси → Добавить прокси → MTProto** и перенесите сервер, порт и секрет из закрытого файла. Названия пунктов немного отличаются между платформами. Ссылку можно передавать только тем, кому нужен доступ.

Для SOCKS5 откройте `.local/telegram-socks/access.md` или перенесите его реквизиты вручную в настройках Telegram. SOCKS5 использует тот же приоритетный пул и закрывает исходящие соединения, если все выходы недоступны. Повторная установка только этого компонента:

```bash
python3 scripts/vpnctl.py deploy-telegram-socks
```

При уже включённом VPN обращения к собственным MTProto/SOCKS5/DD должны оставаться на входном сервере. Для этого добавлены три точных TCP-правила для `${VPN_ENTRY_ADDRESS}` и клиентских портов прокси: они направляют только этот трафик к соответствующим loopback backend. Правила стоят после глобальных блокировок, авторизация VPN и самих прокси сохраняется. Прочие назначения и UDP идут прежним путём.

С ноутбука, где подготовлены закрытые файлы в `.local/telegram-probe/`:

```bash
# Только проверка настоящими Telegram-клиентами через фактический Auto-профиль.
python3 scripts/verify_telegram_proxy_clients.py --interface en0

# Безопасная установка маршрутов: локальная сборка pinned gotd, preflight,
# API без рестарта VPN, автооткат через 180 секунд при неуспешной проверке.
python3 scripts/deploy_telegram_local.py --interface en0
```

`en0` — физический интерфейс этого Mac. Выбор интерфейса не доказывает обход активного Network Extension или прозрачного прокси. На другом ноутбуке передайте свой интерфейс или опустите этот флаг. Нужен Go для локальной сборки проверочного клиента. Закрытый каталог содержит `sing-box`, `subscription.json` с действующим `sub_id`, необязательный `dcs.json` и `telegram-probe`; реквизиты прокси берутся из access-файлов выше. При отсутствии `dcs.json` MTProto-проверка сначала получает актуальные DC из Telegram. Файлы доступа переносите отдельно от Git. Установщик сохраняет резервную копию и независимый watchdog; подтверждение требует успешного полного обмена через все три входа. Повторная проверка уже настроенного состояния: `deploy_telegram_local.py --verify-existing --interface en0`. Переход с прежних двух правил добавляет только DD-обработчик; откат сохраняет два исходных.

## Добавление выходного сервера

Новый резерв добавляется в **VPN Auto**, отдельный список у MTProto не нужен. Следуйте [инструкции добавления сервера с ноутбука](add-server-from-laptop.md): для уже настроенного выхода добавьте строку в конец `failover.egresses`, затем выполните:

```bash
python3 scripts/vpnctl.py update-failover-pool
```

Для чистого VPS используйте описанную там команду `add_host.py --pool auto`. Сохраните прежний порядок, чтобы не менять основной IP без необходимости. После обновления пула клиентский адрес, порт и секрет Telegram остаются прежними; переустанавливать MTProto не требуется.

## Проверка службы

20 ноября 2026 года публичный MTProto-вход проверен с ноутбука для DC2, DC4 и медиа-DC2: FakeTLS и ответ Telegram `resPQ` с совпавшим nonce прошли. В изолированной копии после отключения основного выхода обмен прошёл через NL. При отключении всех трёх выходов копия отклонила MTProto RPC. Рабочие VPN-процессы сохранили PID.

После добавления локальных маршрутов все три настоящих Telegram-клиентских пути поверх VPN Auto прошли полный DH/auth-key обмен и `help.getNearestDC`: MTProto FakeTLS, SOCKS5 с авторизацией и MTProto DD. Исходные VPN-входы, UUID и PID сохранены.

На тестовом Mac SOCKS5 проходит авторизацию и HTTPS, но CONNECT к Telegram не доходит до сервера. Это повторено на другом хосте: данные авторизации приходят, следующего запроса нет. Причина находится до серверного обработчика; отделить действие прозрачного прокси на ноутбуке от ограничений Wi-Fi этой проверкой нельзя. Установленный DD прошёл gotd для основных DC1–DC5 и официальный TDLib для DC2/DC4, но эти проверки также не доказывают доступность без VPN. Медиа DC поддерживаются по основному номеру; отдельный CDN203 этот vendor не поддерживает, полная CDN-совместимость не заявляется. Дополнительные входы и WEB описаны в [инструкции Telegram-прокси](telegram-proxies.md).

На входном сервере:

```bash
sudo systemctl is-active vpn-mtproto.service
sudo systemctl is-active vpn-mtproto-dd.service
sudo systemctl is-active vpn-telegram-socks.service
sudo journalctl -u vpn-mtproto.service --since '10 minutes ago'
```

Повторная проверка реального протокола выполняется скриптом `verify_mtproto.py` с закрытой конфигурацией. Скрипт `verify_mtproto_failover.py --failed 1 --expected-ip "${VPN_NL_ADDRESS}"` проверяет резерв в отдельных процессах, а `--failed 3` проверяет блокировку при отказе всего пула. Скрипты загружаются с ноутбука на сервер в закрытый staging через SSH. Проверка TCP-порта добавлена в существующий Prometheus. [Конфигурация mtg 2.3.0](https://github.com/9seconds/mtg/blob/v2.3.0/example.config.toml).
