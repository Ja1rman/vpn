# Две подписки VPN

1. **Обычная подписка.** Обновите существующую подписку `https://${VPN_ENTRY_ADDRESS}:${VPN_SUBSCRIPTION_PORT}/sub/<SubID>` в приложении. VLESS с открытым TCP автоматически выдаются через новые TLS-порты. UUID и маршруты соответствуют исходным привязкам x-ui. Shadowsocks и прежние REALITY-профили также доступны.
2. **Автоматический резерв.** Добавьте отдельную подписку `https://${VPN_ENTRY_ADDRESS}:${VPN_AUTO_SUBSCRIPTION_PORT}/sub/<SubID>`, оставив тот же идентификатор из старой ссылки. Путь `/failover/<SubID>` на `${VPN_AUTO_SUBSCRIPTION_PORT}` также поддерживается. Оба адреса отдают один профиль **VPN Auto** для Xray, NekoBox и Hiddify. Идентификатор является секретом; в репозитории и логах его нет.

TLS-профили обычной подписки формируются штатными **Hosts** x-ui для каждого привязанного клиента, включая новых. Сертификат проверяется по публичному IP. Порты назначены следующим образом.

| Привязка в x-ui | TLS-порт в подписке |
| --- | --- |
| `${VPN_VLESS_AUTH_PORT}` | `${VPN_STANDARD_TLS_PORT}` |
| `${VPN_PRIMARY_VLESS_PORT}` | `${VPN_PRIMARY_TLS_PORT}` |
| `${VPN_NL_RELAY_VLESS_PORT}` | `${VPN_NL_RELAY_TLS_PORT}` |
| `${VPN_THIRD_VLESS_PORT}` | `${VPN_THIRD_TLS_PORT}` |

VPN Auto предпочитает VLESS с TLS на `${VPN_AUTO_TLS_PUBLIC_PORT}` для существующих и новых клиентов с привязкой к основному VLESS `${VPN_VLESS_AUTH_PORT}`. В NekoBox или Hiddify обновите именно подписку, затем выберите её единственный профиль **VPN Auto** и переподключитесь. Порт, SNI, fingerprint Chrome и UUID импортируются автоматически; проверку сертификата отключать не нужно. Ранее импортированный TLS-профиль на `${VPN_AUTO_TLS_PORT}` сохранён, но обновление подписки переключает приложение на дополнительный публичный вход. При отсутствии основного VLESS в выдаче используется прежний источник REALITY. TCP к доменам **.ru, .рф и .ру** выходит напрямую с IPv4 `${VPN_ENTRY_ADDRESS}`. Если клиент передал только IPv4, для HTTP и TLS на портах `${VPN_WEB_HTTP_PORT}` и `${VPN_WEB_HTTPS_PORT}` используется видимое имя сайта. Когда имя неизвестно, а также для UDP (включая HTTP/3), сохраняется прежний маршрут.

Для штатного User-Agent NekoBox Android версии от 1.3.8 Auto-подписка отдаёт один sing-box outbound JSON с тем же именем **VPN Auto** и явным `multiplex.enabled=false`. Это обходит сохранение несовместимых MUX-настроек старым импортёром VLESS. Имя записи, UUID, endpoint и проверка TLS сохраняются; выбранный профиль не удаляется. Hiddify, Xray и прочие клиенты получают прежнюю VLESS URI-выдачу. Обычная подписка и REALITY fallback сохраняют прежний формат. Не меняйте User-Agent подписки вручную: по нему определяется совместимая выдача.

`.ру` учтён в правиле, но такой зоны нет в [публичном списке IANA](https://data.iana.org/TLD/tlds-alpha-by-domain.txt); правило само по себе не добавляет её в DNS.

Остальной трафик использует первый доступный выход: **ihor → breeze-reef → srv-41969**. Система периодически проверяет выходы по HTTPS. После сбоя новые соединения используют резерв; оборванное соединение приложение должно открыть заново. При восстановлении более приоритетного выхода новые соединения возвращаются к нему. При отказе всех зарубежных выходов остальной трафик не переключается на прямой маршрут.

Три выхода находятся на разных узлах. Обе подписки по-прежнему зависят от общего входного сервера `${VPN_ENTRY_ADDRESS}`: его полный отказ эта схема не переживает.

[Как добавить новый выход в VPN Auto с ноутбука](add-server-from-laptop.md) · [Как выдать подписку новому клиенту](create-user-subscriptions.md).

## Развёртывание и откат

REALITY и TLS VPN Auto передают исходный UUID в существующий VLESS `${VPN_LOOPBACK_IP}:${VPN_VLESS_AUTH_PORT}` с локального адреса `${VPN_AUTO_SOURCE_IP}`. Правило маршрутизации совпадает одновременно по этому адресу и входу `${VPN_VLESS_AUTH_PORT}`, после существующих глобальных блокировок. Вход `${VPN_AUTO_REALITY_PORT}` хранит прежний список REALITY-клиентов. Публичный `${VPN_AUTO_TLS_PUBLIC_PORT}` прозрачно передаёт TCP через `vpn-auto-access.socket` в существующий TLS-вход `${VPN_AUTO_TLS_PORT}`; тот снимает TLS и передаёт VLESS без изменений. Xray проверяет UUID, права и квоты, поэтому отдельный список TLS-пользователей синхронизировать не требуется. Четыре обычных TLS-входа из таблицы выше передают данные на соответствующие исходные порты с `${VPN_LOOPBACK_IP}`, сохраняя их маршрутизацию.

Основной SOCKS и API отдельного Xray `vpn-failover-pool.service` доступны только на loopback `${VPN_FAILOVER_SOCKS_PORT}/${VPN_AUTO_API_PORT}`. Порядок и исходные теги задаются в `inventory/hosts.json → failover.egresses`. Конфигурация собирается на входном сервере из уже настроенных выходов x-ui и старого пула, без выгрузки ключей в Git. У обычной подписки есть отдельный пул `vpn-balancer` на `${VPN_BALANCER_SOCKS_PORT}`. Установщики TLS отказываются менять отличающиеся nginx-конфиги и systemd units. При их точном совпадении разрешено атомарно обновить только закрытые Python-помощники и окружение, проверив неизменность процессов; служба не перезапускается.

Правило прямого выхода задаётся полем `failover.direct_ru_ipv4`. Это ожидаемый публичный адрес сервера, даже если провайдер выдаёт его через NAT. В действующем пуле правило добавляет `sudo python3 enable_auto_ru.py payload/hosts.json` из закрытого staging; дополнительный SOCKS-вход для распознавания имени доступен только на loopback `${VPN_AUTO_SNIFF_PORT}`. Добавление следующих резервов сохраняет это правило.

Для чистого развёртывания на уже настроенном входном сервере:

1. `python3 scripts/vpnctl.py stage-failover` — выгрузить скрипты и inventory в закрытый staging. Перейдите в напечатанный каталог под SSH.
2. `sudo python3 failover_variant.py install pool payload/hosts.json` — поднять только новый пул. `sudo python3 verify_priority_backup.py --config /etc/vpn-failover/pool.json --failed 1 --expected-ip "${VPN_NL_ADDRESS}"` и вариант с `--failed 2 --expected-ip "${VPN_THIRD_EXIT_ADDRESS}"` проверяют переключение в копиях.
3. `sudo python3 enable_failover_variant.py apply --legacy-ip "${VPN_NL_ADDRESS}" --variant-ip "${VPN_PRIMARY_EXIT_ADDRESS}"` — добавить маршрут через API с контрольными TCP/UDP-проверками и автоматическим откатом. Аргументы должны соответствовать текущим внешним IP.
4. `sudo python3 failover_variant.py install entry payload/hosts.json` — поднять новый вход. Проверьте его с внешнего клиента, затем `sudo python3 install_failover_subscription.py install --service-script failover_subscription.py`.
5. На ноутбуке: `python3 scripts/render.py`, затем `python3 scripts/vpnctl.py refresh-failover-monitoring` — горячо перечитать правила и проверки.

Служба подписок на `${VPN_AUTO_SUBSCRIPTION_PORT}` фильтрует существующую HTTPS-выдачу x-ui и не меняет её. Таймер каждые пять минут проверяет текущие файлы TLS x-ui и атомарно обновляет закрытую копию для нового сервиса. Сам выпуск и обновление исходного сертификата остаются у существующей системы x-ui.

После установки подписок включите автоматическую выдачу для новых клиентов с ноутбука командой `python3 scripts/vpnctl.py deploy-auto-onboarding`. Она запускает отдельный TLS-вход, проверяет его и обновляет только HTTPS-выдачу на `${VPN_AUTO_SUBSCRIPTION_PORT}`. Контрольные ранее выданные профили сверяются побайтно до и после обновления. Существующие VPN-входы и Xray не перезапускаются.

Намеренная смена Auto-профиля выполняется отдельным `install_failover_subscription.py upgrade --allow-profile-update` в закрытом staging: проверка допускает только тот же UUID и адрес, настроенный новый TLS-порт и точные параметры SNI, Chrome и XUDP. Без этого флага изменение ранее выданного профиля отклоняется. Обычная подписка при таком обновлении не меняется.

Для автоматической выдачи совместимых VLESS в обеих подписках выполните на ноутбуке `python3 scripts/vpnctl.py deploy-xray-subscriptions`. Команда поднимает четыре обычных TLS-входа, проверяет кандидаты native Xray, обновляет обработчик VPN Auto и публикует штатные Hosts x-ui. Затем она проверяет реальные VLESS-ссылки из обеих подписок, HTTPS и UDP DNS. В случае ошибки итоговой проверки новые Host-записи откатываются. Уже установленные TLS-входы проверяются повторно. Основной Xray и существующие VPN-сессии при этом не перезапускаются.

Для полного отключения VPN Auto сначала переведите его пользователей на обычные профили, затем остановите `vpn-failover-subscription.service`, `vpn-failover-entry.service` и `vpn-auto-tls-frontend.service`. Откат маршрута выполняется командой `sudo python3 enable_failover_variant.py rollback <каталог-отката>`. Помощник сверяет состояние перед откатом и применяет его через API Xray. Текущий маршрут сохранён в `/var/backups/vpn-infra/failover-variant-20261110T171343394051Z`.

## Алерты

Раньше почта сообщала об одном старом NL-пуле. По истории 9–10 ноября он был недоступен около 16 ч 29 мин; после восстановления отдельные TCP-проверки NL продолжали срабатывать. Это не было проверкой трёх физических выходов.

- Критический `VpnFailoverUnavailable`: две минуты не отвечает вход или основной порт авторизации либо проваливаются обе HTTPS-проверки нового пула.
- `VpnLegacyEgressUnavailable`: предупреждение об отказе обычного пула вместе с его резервами. В нём после трёх транспортов `breeze-reef` настроены независимые `ihor` и `srv-41969`.
- Отдельные порты предупреждают после трёх минут. Alertmanager группирует сообщения по хосту и подавляет повторяющиеся предупреждения о компонентах узла, если уже есть алерт о недоступности его метрик. Краткие восстановления не открывают сразу новый эпизод. SMTP и получатели не менялись.

10 ноября проверены обе подписки для девяти пользователей и внешний трафик по обоим входам. В изолированной копии последовательно отключены один и два выхода; через каждый резерв прошли четыре HTTPS и четыре UDP DNS проверки. Рабочий Xray и старый HTTPS-туннель пережили изменение без перезапуска.
