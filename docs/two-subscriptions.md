# Две подписки VPN

1. **Как сейчас.** Оставьте существующую подписку `https://212.22.70.156:2096/sub/<SubID>` без изменений. В ней сохранены прежние профили, их порты и маршруты.
2. **Автоматический резерв.** Добавьте отдельную подписку `https://212.22.70.156:2097/sub/<SubID>`, оставив тот же идентификатор из старой ссылки. Путь `/failover/<SubID>` на `2097` также поддерживается. Оба адреса отдают один профиль **VPN Auto** для NekoBox и Hiddify. Идентификатор является секретом; в репозитории и логах его нет.

VPN Auto подключается по VLESS/REALITY к порту `33174`. TCP к доменам **.ru, .рф и .ру** выходит напрямую с IPv4 `212.22.70.156`. Если клиент передал только IPv4, для HTTP и TLS на портах 80 и 443 используется видимое имя сайта. Когда имя неизвестно, а также для UDP (включая HTTP/3), сохраняется прежний маршрут.

`.ру` учтён в правиле, но такой зоны нет в [публичном списке IANA](https://data.iana.org/TLD/tlds-alpha-by-domain.txt); правило само по себе не добавляет её в DNS.

Остальной трафик использует первый доступный выход: **ihor → breeze-reef → srv-41969**. Система периодически проверяет выходы по HTTPS. После сбоя новые соединения используют резерв; оборванное соединение приложение должно открыть заново. При восстановлении более приоритетного выхода новые соединения возвращаются к нему. При отказе всех зарубежных выходов остальной трафик не переключается на прямой маршрут.

Три выхода находятся на разных узлах. Обе подписки по-прежнему зависят от общего входного сервера `212.22.70.156`: его полный отказ эта схема не переживает.

[Как добавить новый выход в VPN Auto с ноутбука](add-server-from-laptop.md).

## Развёртывание и откат

Новый frontend передаёт исходный UUID в существующий VLESS `127.0.0.1:46738`, используя локальный адрес `127.0.0.2`. Единственное добавленное правило совпадает одновременно по этому адресу и входу `46738`, после существующих глобальных блокировок. Остальные подключения продолжают обрабатываться прежними правилами. Список клиентов фронтенда, как и у совместимого входа `33173`, — снимок; основной Xray проверяет текущие права. При смене UUID обновите оба совместимых фронтенда.

Основной SOCKS и API отдельного Xray `vpn-failover-pool.service` доступны только на loopback `11092/11093`. Порядок и исходные теги задаются в `inventory/hosts.json → failover.egresses`. Конфигурация собирается на входном сервере из уже настроенных выходов x-ui и старого пула, без выгрузки ключей в Git. Старый `vpn-balancer` на `11090` не затрагивается. Установщики отказываются перезаписывать отличающуюся действующую установку.

Правило прямого выхода задаётся полем `failover.direct_ru_ipv4`. Это ожидаемый публичный адрес сервера, даже если провайдер выдаёт его через NAT. В действующем пуле правило добавляет `sudo python3 enable_auto_ru.py payload/hosts.json` из закрытого staging; дополнительный SOCKS-вход для распознавания имени доступен только на loopback `11094`. Добавление следующих резервов сохраняет это правило.

Для чистого развёртывания на уже настроенном входном сервере:

1. `python3 scripts/vpnctl.py stage-failover` — выгрузить скрипты и inventory в закрытый staging. Перейдите в напечатанный каталог под SSH.
2. `sudo python3 failover_variant.py install pool payload/hosts.json` — поднять только новый пул. `sudo python3 verify_priority_backup.py --config /etc/vpn-failover/pool.json --failed 1 --expected-ip 144.31.34.165` и вариант с `--failed 2 --expected-ip 13.143.134.214` проверяют переключение в копиях.
3. `sudo python3 enable_failover_variant.py apply --legacy-ip 144.31.34.165 --variant-ip 95.81.127.144` — добавить маршрут через API с контрольными TCP/UDP-проверками и автоматическим откатом. Аргументы должны соответствовать текущим внешним IP.
4. `sudo python3 failover_variant.py install entry payload/hosts.json` — поднять новый вход. Проверьте его с внешнего клиента, затем `sudo python3 install_failover_subscription.py install --service-script failover_subscription.py`.
5. На ноутбуке: `python3 scripts/render.py`, затем `python3 scripts/vpnctl.py refresh-failover-monitoring` — горячо перечитать правила и проверки.

Служба подписок на `2097` фильтрует существующую HTTPS-выдачу x-ui и не меняет её. Таймер каждые пять минут проверяет текущие файлы TLS x-ui и атомарно обновляет закрытую копию для нового сервиса. Сам выпуск и обновление исходного сертификата остаются у существующей системы x-ui.

Если потребуется отключить новый вариант, сначала остановите только `vpn-failover-subscription.service` и `vpn-failover-entry.service`. Откат маршрута: `sudo python3 enable_failover_variant.py rollback <каталог-отката>`. Помощник сверяет состояние перед откатом; он не откатывает чужие параллельные изменения и не перезапускает Xray. Для текущего включения маршрут сохранён в `/var/backups/vpn-infra/failover-variant-20261110T171343394051Z`.

## Алерты

Раньше почта сообщала об одном старом NL-пуле. По истории 9–10 ноября он был недоступен около 16 ч 29 мин; после восстановления отдельные TCP-проверки NL продолжали срабатывать. Это не было проверкой трёх физических выходов.

- Критический `VpnFailoverUnavailable`: две минуты не отвечает вход или основной порт авторизации либо проваливаются обе HTTPS-проверки нового пула.
- `VpnLegacyEgressUnavailable`: отдельное предупреждение для старых профилей, даже когда VPN Auto работает.
- Отдельные порты предупреждают после трёх минут. Alertmanager группирует сообщения по хосту и подавляет повторяющиеся предупреждения о компонентах узла, если уже есть алерт о недоступности его метрик. Краткие восстановления не открывают сразу новый эпизод. SMTP и получатели не менялись.

10 ноября проверены обе подписки для девяти пользователей и внешний трафик по обоим входам. В изолированной копии последовательно отключены один и два выхода; через каждый резерв прошли четыре HTTPS и четыре UDP DNS проверки. Рабочий Xray и старый HTTPS-туннель пережили изменение без перезапуска.
